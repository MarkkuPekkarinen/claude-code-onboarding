# Advanced Chunking Guide

Reference for chunking strategies beyond the basic decision tree. Apply after completing SKILL.md Step 2.

---

## 1. Chunking Techniques Catalog

### 1.1 Document-Aware (Default)
Split on structural signals: Markdown headings, PDF section headers, HTML tags.
- Best for: structured docs (manuals, policies, knowledge bases)
- Overlap: 10–20% of chunk size
- Gotcha: fails on scanned PDFs without structure — use OCR + hierarchical parsing first

### 1.2 Parent-Child (Small-to-Big Retrieval)
Store two granularities. Index small children (200–400 tok) for precision; return parent (1500–3000 tok) for context.
- Best for: narrow factual questions that need surrounding context
- Implementation: `parent_chunk_id` FK on children; retrieval returns parent when child matches
- Gotcha: parent must not exceed generation context window after packing

### 1.3 Sentence-Window
Each chunk is one sentence. Retrieve sentence; return ±N sentences for context.
- Best for: very short factual queries against dense documents
- N=2 (5-sentence window) is a common starting point
- Gotcha: higher index size; tune N before production

### 1.4 Semantic Chunking
Split when embedding similarity between adjacent sentences drops below threshold.
- Best for: documents with topic shifts not marked by headings
- Threshold: cosine similarity < 0.85 is a common starting point
- Gotcha: slower ingestion; adds LLM/embedding cost per document

### 1.5 Contextual Retrieval
Before storing each chunk, prepend a 1–2 sentence context summary generated by an LLM.
- Example: "This chunk is from Section 4 of the vendor contract for Acme Corp, covering late payment penalties."
- Best for: chunks that lose meaning standalone (mid-document paragraphs)
- Cost: one LLM call per chunk at ingestion — expensive at scale; use selectively
- Deferred to v2 in the default stack

### 1.6 Late Chunking
Embed the full document first; then chunk the contextual embeddings (not the raw text).
- Preserves cross-chunk context in embedding space
- Requires model support (e.g., JinaAI models with late chunking)
- Deferred to v2

### 1.7 Agentic Chunking
Use an LLM to decide chunk boundaries based on "proposition density" — each chunk = one complete proposition.
- Best for: highly heterogeneous corpora where structural rules fail
- Cost: high — one LLM call per few sentences; only justified for high-value corpora
- Deferred to v2

### 1.8 Adaptive Chunking by Content Type
Use different strategies per file type in the same corpus:

| Content Type | Strategy |
|---|---|
| Policy / procedure docs | Document-aware on headings |
| FAQ / Q&A pages | Natural unit (Q+A pair), no split |
| Long legal contracts | Parent-child, parents = clauses |
| Emails / tickets | Full message = one chunk (usually short) |
| Code files | Function/class boundary splits |
| Tables / spreadsheets | Row-as-chunk or section-as-chunk; use LlamaParse |

### 1.9 Recursive Retrieval
Index summaries at multiple granularities (doc → section → paragraph). Route query to the right level.
- Best for: multi-hop questions that need to navigate document hierarchy
- Implementation complexity: high; deferred to v2

### 1.10 Table Chunking
Tables require special handling — standard token-based splitting breaks mid-row and loses column headers. See `references/table-chunking-strategy.md` for the full guide.

Quick rules:
- Small tables (≤ 20 rows): keep as one chunk, prepend section heading
- Medium tables (21–100 rows): row-group chunks of N rows, **always repeat header row**
- Large tables: store three representations (plain text, Markdown, JSON) filtered at query time by `content_type`
- Required metadata: `content_type: table`, `table_headers`, `table_row_range`, `parent_table_id`

## 2. Chunk Quality Scoring at Ingestion

Don't ingest garbage. Score each chunk before writing to the vector store.

### Quality Signals
| Signal | How to Measure | Reject Threshold |
|---|---|---|
| Token count | `len(tokenize(chunk))` | < 50 tokens |
| Lexical diversity | unique tokens / total tokens | < 0.3 |
| Dictionary word ratio | real words / total tokens | < 0.6 |
| OCR garble detection | character n-gram anomaly | > 0.15 garble rate |
| Truncation detection | chunk ends mid-sentence | flag for review |
| Duplication | minhash against recent chunks | cosine > 0.97 = duplicate |

### Implementation Pattern
```python
def quality_score(chunk_text: str) -> float:
    tokens = tokenize(chunk_text)
    if len(tokens) < 50:
        return 0.0  # reject
    diversity = len(set(tokens)) / len(tokens)
    dict_ratio = count_real_words(tokens) / len(tokens)
    return (diversity + dict_ratio) / 2  # 0–1 score

# At ingestion:
score = quality_score(chunk.text)
if score < 0.5:
    log.warning("Low quality chunk skipped", chunk_id=chunk.id, score=score)
    continue
chunk.metadata["quality_score"] = score
```

## 3. OCR Quality Gates (§6.2)

Parser quality is the single largest preventable source of RAG failure. Gate OCR output before chunking.

### Gate 1 — Confidence Threshold
Most OCR engines output per-character or per-word confidence.
- Reject pages where average confidence < 0.80
- Flag pages where confidence is 0.80–0.90 for human review

### Gate 2 — Garbled Text Detection
OCR failures produce character soup: "Th3 c0ntr@ct sp3cif1es..."
```python
import re
GARBLE_PATTERN = re.compile(r'[^\w\s.,;:!?()\-\'\"]{3,}')  # 3+ consecutive non-word chars

def detect_garble(text: str) -> float:
    matches = GARBLE_PATTERN.findall(text)
    garble_chars = sum(len(m) for m in matches)
    return garble_chars / max(len(text), 1)

# Reject if garble_rate > 0.15
```

### Gate 3 — Sample Verification
For new document types, manually verify 5–10 parsed samples before bulk ingestion.
- Check: table structure preserved? Headers detected? Footnotes separated?
- A single parser bug repeated 10,000 times silently breaks retrieval

### Parser Selection by Document Type
| Document Type | Recommended Parser |
|---|---|
| Mixed formats (Word, HTML, TXT) | Unstructured.io |
| Table-heavy PDFs | LlamaParse or Camelot |
| Scanned PDFs | Unstructured.io with OCR mode + quality gates |
| Markdown | Direct split — no parser needed |
| Code files | Tree-sitter for language-aware splits |

## 4. Metadata Schema (§12)

Required metadata fields for every chunk. Missing fields break filtering, versioning, and GDPR deletion.

| Field | Type | Required | Purpose |
|---|---|---|---|
| `document_id` | uuid | ✅ | Groups all chunks from one source document |
| `chunk_id` | varchar | ✅ | Stable identifier: `{doc_id}-v{version}-{chunk_index}` |
| `tenant_id` | varchar | ✅ | Multi-tenancy filter chokepoint |
| `access_level` | varchar | ✅ | Security filter (e.g. public, internal, confidential) |
| `document_version` | int | ✅ | Incremented on document update |
| `content_hash` | varchar | ✅ | SHA-256 of chunk text — used for dedup and diff-ingestion |
| `updated_at` | timestamp | ✅ | Used for freshness ranking and cache invalidation |
| `section` | varchar | ✅ | Document section / heading path |
| `page` | int | conditional | Page number (PDF/DOCX); null for HTML/Markdown |
| `created_at` | timestamp | ✅ | Ingestion timestamp |
| `effective_from` | date | domain-specific | Start of validity window (contracts, policies) |
| `effective_to` | date | domain-specific | End of validity window; used for temporal filtering |
| `parent_chunk_id` | varchar | if parent-child | FK to parent chunk |
| `source_uri` | varchar | ✅ | Original document URL or path — used in citations |
| `embedding_model` | varchar | ✅ | Model name + version — required for migration |
| `quality_score` | float | recommended | Ingestion quality score (0–1) — for debug and filtering |
| `embedding_model` | varchar | ✅ | Embedding model name (e.g. `text-embedding-3-large`) |
| `embedding_version` | varchar | ✅ | Model version or date pinned — required for migration tracking |
| `embedding_dimensions` | int | ✅ | Vector dimension (e.g. 1536) — detects dimension mismatch at query time |
| `task_type` | varchar | ✅ | `RETRIEVAL_DOCUMENT` at ingest; `RETRIEVAL_QUERY` at query — must match model API |
| `embedded_at` | timestamp | ✅ | When this chunk was embedded — used to detect stale embeddings after model update |

### Stable Chunk ID Scheme
```
chunk_id = f"{document_id}-v{document_version}-{chunk_index:04d}"
# Example: "policy-lease-2024-v3-0012"
```
Never use auto-increment IDs for chunks — they change on re-ingestion and break golden sets.

## 5. Ingestion Update Strategies (§5.3)

| Strategy | When to Use | Cost | Risk |
|---|---|---|---|
| **Full re-ingest** | Schema change, embedding model change | High | Safe — start fresh |
| **Document-level diff** | Most updates (new doc version uploaded) | Medium | Safe — compare `content_hash` at doc level |
| **Chunk-level diff** | Frequent partial edits | Low | Medium — chunk boundary drift can cause subtle misses |
| **Append-only** | Immutable docs (audit logs, historical records) | Very Low | Low — never delete, only add |

**Recommended default:** document-level diff using `content_hash`.
```python
existing_hash = get_stored_hash(document_id)
new_hash = sha256(document_bytes)
if existing_hash == new_hash:
    return  # no change — skip ingestion
# else: delete old chunks, re-ingest
delete_chunks_for_document(document_id)
ingest_document(document)
```
